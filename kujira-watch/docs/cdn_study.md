# CDN勉強ノート（kujira-watch実例つき）

CDNの基礎を、このサイト（Next.js 16 + Vercel）で実際に動いている仕組みに沿って整理する。
「一般論 → 自サイトのどこで使われているか」の順で読む。

## 1. CDNとは

CDN（Content Delivery Network）は、世界中に分散配置されたキャッシュサーバー群（エッジ）。
利用者は自分に一番近いエッジに接続し、エッジにキャッシュがあれば（HIT）オリジンサーバー
まで行かずに応答が返る。効果は主に3つ。

1. **速い**: 東京の読者は東京のエッジから受け取る。物理距離＝レイテンシが減る
2. **オリジン保護**: キャッシュHITした分だけオリジン（Next.jsの関数・microCMS・Supabase）に
   リクエストが届かない。API課金・関数実行時間の節約になる
3. **耐障害性**: stale-while-revalidateを使えば、オリジンが遅い/落ちていても
   期限切れの古いキャッシュを返してしのげる

このサイトでは **Vercel Edge Network** がCDN。デプロイすると自動で全ページ・全アセットが
エッジ経由になる。CDNを「使うかどうか」ではなく「どうキャッシュさせるか」が設計ポイント。

## 2. キャッシュを制御するHTTPヘッダー

CDNへの指示はレスポンスの `Cache-Control` ヘッダーで行う。よく使うディレクティブ:

| ディレクティブ | 意味 | 対象 |
|---|---|---|
| `max-age=60` | 60秒キャッシュしてよい | ブラウザ・CDN両方 |
| `s-maxage=60` | 60秒キャッシュしてよい | **共有キャッシュ（CDN）のみ** |
| `stale-while-revalidate=300` | 期限切れ後も300秒間は古い応答を返してよい。その間に裏で再取得 | CDN |
| `public` / `private` | 共有キャッシュに保存してよい / ブラウザのみ | - |
| `no-store` | 一切キャッシュ禁止 | 両方 |
| `immutable` | 期限内は再確認すら不要（内容が変わらない前提） | ブラウザ |

**`s-maxage` と `max-age` を分ける理由**: CDNは自分でパージ（削除）できるが、
ユーザーのブラウザキャッシュは配信後にコントロールできない。だから
「CDNには長く、ブラウザには短く（または0）」が定石。

**stale-while-revalidate（SWR）** はCDNの肝。TTL切れの瞬間に全員をオリジン行きにする
のではなく、「古いのを即返す→裏で1回だけ再取得→次から新しいのを返す」ので、
体感速度を落とさずに鮮度を保てる。ReactのデータフェッチライブラリSWRの名前の由来もこれ。

## 3. キャッシュキー — 「何単位でキャッシュされるか」

CDNは基本的に **URL（パス+クエリ文字列）単位** でキャッシュを持つ。

- `/api/articles?offset=0` と `/api/articles?offset=12` は別キャッシュ
- `/api/stocks/search?q=トヨタ` と `?q=ソニー` も別キャッシュ

同じURLでも内容が変わりうる場合（例: HTMLとRSCペイロード）は `Vary` ヘッダーや
クエリパラメータでキャッシュを分離する。Next.jsは `_rsc` クエリパラメータを
キャッシュキーの識別子として使い、HTML応答とクライアントナビゲーション用RSC応答が
混ざらないようにしている（詳細: `node_modules/next/dist/docs/01-app/02-guides/cdn-caching.md`）。

## 4. このサイトでのCDN活用マップ

### (a) 静的アセット — 最強のキャッシュ（Next.jsが自動設定）

`/_next/static/` のJS/CSSはファイル名にコンテンツハッシュが入る
（内容が変わればURLも変わる）ので、`public, max-age=31536000, immutable`（1年+不変）。
デプロイのたびに新URLになるため、キャッシュの無効化を考えなくてよい。
**「URLに内容のハッシュを入れて永久キャッシュ」はCDN設計の最重要パターン。**

### (b) ページ — ISR = CDNキャッシュ + 裏側再生成

各ページの `export const revalidate = 60` などのISR設定は、CDN的には
`s-maxage=60, stale-while-revalidate=<長期>` として配信される。
つまり **ISRとは「CDNキャッシュ + オリジン側の再生成管理」のNext.js流パッケージ**。
記事ページ60秒、ランキング3600秒など、更新頻度に応じてページごとにTTLを変えている。

### (c) APIルート — 今回追加した明示的キャッシュ

Route HandlerはNext.js 15以降デフォルトでキャッシュされない（毎回オリジン実行）。
そこで応答に `Cache-Control` を明示してCDNに任せる:

| ルート | 設定 | 根拠 |
|---|---|---|
| `/api/articles` | `s-maxage=60, swr=300` | 無限スクロール用。記事ページのISR(60s)と同鮮度 |
| `/api/stocks/search` | `s-maxage=300, swr=3600` | 検索候補の増減は記事投稿時のみ（最短毎時） |
| `/api/watchlist-latest` | `s-maxage=300, swr=600` | 開示スキャンが毎時なので5分で十分 |
| `/feed.xml` | `export const revalidate = 300`（ISR化） | RSSリーダーの定期巡回を毎回microCMSに通さない |

### (d) キャッシュ**しない**もの — 何を除外するかも設計のうち

- `/api/counter`（訪問者カウンター）: **POST**。CDNはPOST/PUT/DELETEを
  キャッシュしない（するべきでもない）。カウントの加算という副作用があるため、
  仮にGETだったとしても `no-store` にすべきもの
- 認証つき・ユーザー固有の応答（今のサイトには無い）: `private` か `no-store`。
  共有キャッシュに乗せると**他人に別人のデータが配られる**大事故になる。
  CDN事故の定番なので、キャッシュを足すときは「この応答は全員に同じでよいか？」を必ず問う

### (e) 画像 — 画像CDN（変換つきキャッシュ）

`next/image` は `/_next/image?url=...&w=640&q=75` というURLで
「リサイズ・WebP変換した結果」をCDNにキャッシュする。つまり**変換処理そのものが
キャッシュされる**のが画像CDNの価値（microCMS側のimgixも同じ思想）。
microCMSは画像を差し替えるとURL自体が変わるため実質immutableとみなせ、
`minimumCacheTTL` を既定の4時間→31日に延長して再変換コストを削った。

## 5. 動作確認のしかた（HIT/MISSを自分の目で見る）

デプロイ後、レスポンスヘッダーの `x-vercel-cache` を見る:

```bash
curl -sI 'https://kujira-watch.com/api/articles?offset=0' | grep -i -e x-vercel-cache -e cache-control
# 1回目: x-vercel-cache: MISS   （オリジンまで行った）
# 2回目: x-vercel-cache: HIT    （エッジから返った）
# TTL切れ直後: STALE            （古いのを返しつつ裏で再取得 = SWRが働いた瞬間）
```

主な値: `MISS`（オリジン行き）/ `HIT`（エッジから応答）/ `STALE`（期限切れを返して裏で更新）/
`PRERENDER`（ビルド時生成の静的応答）/ `BYPASS`（キャッシュ対象外）。
ブラウザのDevTools > Network でも同じヘッダーが見える。

## 6. 落とし穴メモ

- **キャッシュの無効化（purge）は最難関**: 「コンピュータサイエンスで難しいのは
  キャッシュ無効化と命名の2つ」と言われる定番。時間ベース（TTL+SWR）で設計しておくと
  purge APIを叩く仕組みが不要になり、運用が単純になる。即時反映が必要なものだけ
  on-demand revalidation + CDNパージを組む
- **クエリ文字列もキャッシュキー**: `?utm_source=...` のような無害なパラメータでも
  別キャッシュになりHIT率が下がる。パラメータの種類は最小限に
- **`Set-Cookie` があるとキャッシュされない**: 共有キャッシュにCookieを乗せると
  他人にセッションを配ってしまうため、CDNは自衛的にキャッシュを避ける
- **CDNキャッシュはリージョンごと**: 東京でHITしてもフランクフルトでは最初MISS。
  「1回アクセスしたから全世界で温まった」ではない
