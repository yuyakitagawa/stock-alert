# AdSense審査「有用性の低いコンテンツ」対応

2026-08-24 に AdSense 審査で不承認（理由: 有用性の低いコンテンツ）。
Google のポリシー3本（コンテンツの最小要件 / 独自性のある質の高いコンテンツ /
ウェブマスター品質ガイドライン: 質の低いコンテンツ）に照らして原因を実測し、改善する。

## 実測した原因（2026-08-24）

| ページ種別 | 件数 | 本文の実態 | 判定 |
|---|---|---|---|
| 記事 `/articles/[id]` | 976 | **中央値455字・100%が1,000字未満・98%が600字未満** | 最小要件に不足 |
| 銘柄 `/stocks/[code]` | 664 | 記事1件だけが482件(73%) | cookie cutter |
| 取引日 `/date/[date]` | 223 | 記事1件だけが87件、2件以下が149件 | thin content |
| 投資家 `/investors/[filer]` | 2,972 | 解説文なしが2,152件(72%)、開示1件のみが1,002件 | cookie cutter |

- サイト全URL 4,756件のうち **75%が自動生成の集約ページ**。
- 記事生成プロンプトは「650〜900字」と指示しているのに実出力は455字で、指示自体も薄い。
- 文の完全一致（コピペ）は無いが、全記事が「①誰が何%取得 ②推定金額と株価 ③※推測」の
  3段落テンプレートで、Google の "cookie cutter" に該当する。

## 対応

- [x] 1. 薄い自動生成ページを noindex にする（コスト0）
  - [x] 取引日: 記事3件未満は noindex（223→index 74件）
  - [x] 投資家: 解説文なし or 開示1件のみは noindex（2,972→index 567件）
  - [x] 銘柄: 記事1件のみ かつ 事業内容の説明なしは noindex（664→index 637件）
  - [x] sitemap を noindex 判定と一致させる（判定は lib/pageIndexability.ts に集約）
- [x] 2. 記事生成プロンプトを厚くする（新規記事）
  - [x] Supabase の既存データから独自の事実を追加投入（`build_context_facts()`）
        保有の積み上げ履歴 / その投資家の他の保有銘柄（業種つき） / その銘柄の他の大株主 /

## 2026-08-25 審査員エージェント3体による再監査で判明したこと

「1回目の対応は十分ではない」というオーナーの見立ては正しかった。**Phase 1（noindex）は
本番に1行も出ていなかった。**

### 本番デプロイが24時間以上まるごと失敗していた（最大の発見）

Vercelの本番デプロイが 2026-08-24 22:24 以降すべて Error。最後に成功したビルドは1日前で、
`77ce0f0f`（noindex対応）以降の変更は一つも本番に反映されていなかった。
進捗ファイルの「[x] 薄い自動生成ページを noindex にする」は**コード上は事実だが本番では偽**
だった。原因は独立した2つのビルドエラー:

1. `src/lib/investors.ts` の `getFilersWithProfile` が `unstable_cache` から `Set` を返していた。
   `unstable_cache` は戻り値をJSONで直列化するため `Set` は `{}` になり `.has()` が消える。
   noindex判定を `generateMetadata` で呼ぶようにしたことで、`/investors/[filer]` の
   プリレンダリングが `TypeError: e.has is not a function` で落ちビルドごと失敗していた。
   → 配列でキャッシュしSetは読み出し側で組み立てる（`companyInfo.ts` の既存の書き方に統一）。
2. `(en)/en/articles/[id]` の `DEAL_TYPE_EN[article.dealType].label` が、dealType未設定の
   自社株買い記事で `undefined.label` になり `generateMetadata` が例外を投げていた。
   → オプショナルチェーンでガード。

**教訓: 「実装した」と「本番に出た」は別。以後 noindex/サイトマップ系の変更は必ず
`curl` で本番の実測値を確認してから完了扱いにする。**

### 自社株買い記事の重複が毎時1本ずつ増え続けていた

microCMSの `dealType` はセレクト型で、**選択肢に無い値をPOSTしてもエラーにならず空配列で
保存される**。「自社株買い」はCMS側に選択肢が無いため全記事で空になっており、これが
3か所で無言の不具合を起こしていた。

- `already_published()` が `dealType[contains]自社株買い` で既報判定 → 常に0件＝「未投稿」
  → 毎時の `edinet_blog.yml` が同じ開示を何度でも新規投稿。コンヴァノ(6574)の同一開示から
  **13本の重複記事**が公開され、トップページと `/stocks/6574` が同一タイトルで埋まっていた。
  Googleの言う scaled content abuse に直撃する状態。
- `cleanup_duplicate_blog_articles.py` は `filerName` 空の記事を対象外にしており、
  発行体自身の開示でfilerNameを持たない自社株買い記事を回収できなかった。
- フロント側も `dealType==="自社株買い"` が常に偽になり、`/buybacks` の記事一覧が0件、
  記事ページの「（上限）」表示が「（概算）」に化けていた。

→ すべて `tags` で突き合わせるよう修正（e45963e3）。重複12件は削除済み
（`logs/deleted_duplicate_buyback_articles_20260825.json` にバックアップ）。

## 2026-08-27 記事の数値そのものが誤っていた（薄さより重い問題）

リライトに着手する直前、事実カードの「推定取得金額」が変化幅に対して大きすぎることに気づき、
yfinanceの発行済株式数で検算したところ、**保有総額を「この開示での取得金額」として
公開している記事**が見つかった。全965記事をEDINET開示原本と再照合して是正した。

### 実際にあった誤り

| 記事の記述 | 実際 |
|---|---|
| AGC(5201)「293.7億円で取得」 | 33.2億円（8.8倍） |
| 電通グループ(4324)「189.8億円で取得」 | 11.1億円（17倍） |
| 横浜ゴム(5101)「578.9億円」 | 60.2億円（9.6倍） |
| 日東紡績(3110)「73.8億円分を取得」 | 4.2億円の**売り**（方向も逆） |
| 「Jトラスト、KeyHolderの約30%を取得—41.4億円」 | 保有比率は動いていない |
| 「日本レイが東テクの14.88%を取得、240億円超を投下」 | 保有比率は動いていない |

実在の上場企業・金融機関について、起きていない取引を見出しで断定していた。
薄いコンテンツ以前に誤報であり、YMYLサイトとして最も踏んではいけない部類。

### 原因

`tools/fix_misreported_blog_articles.py` の検出条件が「`ratioChangePct`がEDINETとズレている」
ことを前提にしており、**そのフィールドを保存していなかった時代の記事を素通りさせていた**。
当時の生成側は直前保有割合が取れない開示で「今回比率の全量＝今回動いた分」とみなしており
（この生成側の不具合自体は2026-08-19に修正済み）、その頃の記事が残っていた。

検出条件を2つ追加した:
- (c) 直前保有割合が欠損した開示で、記事が保有比率の全量を変化幅として使った痕跡があるもの。
  過去開示から前回比率を補って判定する（新規の大量保有報告書は全量で正しいので除外）。
- (d) 保有比率が前回と同一（変化幅0pt）なのに推定取得/売却金額を出しているもの。
  担保契約や共同保有者の変更で再提出された変更報告書で、売買は起きていない。

### 結果

- 14本を訂正（タイトル・金額・変化幅・売買方向・本文）
- 売買を伴わない12本を削除（`logs/deleted_misreported_articles_20260827_123840.json`）
- 再照合の結果、**提出者まで一意に特定できた864本に誤報は0件**

### 検証の限界と、集計時の注意

- **100本は開示を一意に特定できない**（提出者名が未保存の旧記事、同一銘柄・同一日に複数の
  提出者がいる開示）。この範囲は誤報の有無を検証できていない。
- 最初の照合では提出者を突き合わせずに「銘柄コード×開示日」だけで開示を引いていたため、
  同じ日に複数の提出者がいる銘柄で無関係な行を拾い、誤報件数を大幅に過大集計した
  （179本・40本という数字を一度出したが、提出者まで一致させると26本だった）。
  **記事と開示の突合は必ず提出者名まで一致させること。**
