# 修整指示レビュー（13ラウンド）

修整指示に対して行った変更を、**観点を変えた13ラウンド**でレビューし、指摘を潰し切ってから完了判定する。1体のレビュアーが1観点だけを見るので、指摘が重複せず観点の抜けも出ない。

使用: `/revision-review <修整指示>`（未実装なら先に実装してから回す）
ラウンド数を変える: `/revision-review <修整指示> --rounds 6`（減らす場合も総合再レビューは必ず最後に残す）

## 前提を先に固める

1. **修整指示を1行に要約**して確定させる。曖昧なら回す前にユーザーへ確認する（13ラウンド回してから前提が違うのが一番の無駄）。
2. レビュー対象の差分範囲を決める。既定は作業ツリー全体。
   ```bash
   git status --short && git diff --stat && git diff origin/main...HEAD --stat
   ```
3. 差分が空ならレビューせず「対象なし」と報告して終わる。

## 13の観点（この順で固定）

| # | 観点 | 見るもの |
|---|---|---|
| 1 | 指示充足 | 指示の要求を全部満たしたか。**指示外の変更を混ぜていないか**（スコープ膨張） |
| 2 | バグ・正しさ | 境界値 / None・NaN / 型 / 例外 / オフバイワン / 空リスト |
| 3 | 特徴量整合性 | `lib/utils.py` の64次元定義を変えていないか。列名・順序・欠損補完・学習と推論の一致（CLAUDE.md §0 No Hallucination） |
| 4 | 戦略規律 | ハードフィルター（down_streak>3, drawdown60<-15%）・βフィルター・drop_prob単独判定を壊していないか（§2） |
| 5 | PIT規律・リーク | 未来情報の混入。株価は対象日の終値、決算は `disc_date <= 対象日` の最新開示か（§0 SQL PIT規律） |
| 6 | データ/IO・コスト | Supabase往復の回数（1クエリにまとめられるか）、N+1、外部APIのリトライ・タイムアウト、Claude API呼び出し数 |
| 7 | CI・運用 | GitHub Actions の実行順・`continue-on-error`・timeout、必須環境変数、失敗しても当日の配信が止まらないか |
| 8 | テスト | 既存 `tests/test_*.py` のデグレ、追加テストの要否、削除した関数のテストが残っていないか（§7） |
| 9 | コード規律・ドキュメント | 実験コード / コメントアウト / 不採用分岐の残骸、README・dev_log の同一コミット更新（§7） |
| 10 | セキュリティ・秘密情報 | APIキー / トークンのログ出力・コミット混入、Supabase service key の露出、外部入力（EDINET・kabutan・microCMS）をそのまま信用していないか |
| 11 | 冪等性・再実行安全性 | 毎時パイプラインを再実行しても二重投稿・重複レコードにならないか（2026-08-17 のブログ重複投稿事故の再発防止）、途中失敗からの復帰 |
| 12 | DBスキーマ・移行 | `supabase/*.sql` のカラム追加/削除が後方互換か、既存行のNULL埋め、参照側（`web/export_to_web.py`・kujira-watch）が追従しているか |
| 13 | 総合再レビュー | 1〜12の指摘が**実際に潰れたか**、修正で新たに壊れていないか、差分が膨らんでいないか |

## 回し方

### ラウンド1〜12

`revision-reviewer` サブエージェントを**観点1つにつき1体**起動する。独立なので **3体ずつ並列**（1〜3 / 4〜6 / 7〜9 / 10〜12）で投げる。各体に渡すのは3つだけ:

- 修整指示（1行要約）
- 差分範囲のコマンド（例: `git diff`）
- 担当観点の名前と「見るもの」

バッチが返るたびに指摘を集約する:

- **重複排除**: 同じ `file:line` + 同じ趣旨は1件に統合。
- **却下**: 根拠のない指摘・観点外の指摘・差分と無関係な既存コードへの指摘は落とす。落とした件数だけ記録する。
- **修正適用**: `B` は全部直す。`M` は原則直す。`m` は差分が膨らむなら見送り（見送りは報告に残す）。
- **論点（`?`）は直さず保留リストに積む**。下記「論点はユーザーに聞く」に従う。
- 修正したら**その時点で該当テストを実行**して壊れていないことを確認する。

## 論点はユーザーに聞く（勝手に決めない）

**論点 = どちらを選んでも何かを失う／指示の読み方が2通り以上ある指摘**。これを AI が「たぶんこっち」で決めて修正するのが一番危ない。**必ずユーザーに聞いてから直す**。

論点として扱うもの:

- **指示の解釈が割れる**: 修整指示をどう読むかで結果が変わる（「直近60日」は営業日か暦日か、等）
- **トレードオフ**: 精度 vs 実行コスト、後方互換 vs 単純さ、網羅性 vs 差分の大きさ — どちらにも損がある
- **規律に触れる**: `lib/utils.py` の64次元定義、ハードフィルター、βフィルター、drop_prob単独判定を変える必要がある（CLAUDE.md §0/§2）
- **数値が動く**: 修正がランキング・バックテスト結果を変えうる（マージ規律の判定が必要）
- **スコープを超える**: 直すには指示の範囲外へ差分を広げる必要がある
- **レビュアー間で矛盾**: 同じ箇所に相反する指摘が出た（どちらが正しいか AI が決めない）

聞き方:

1. **まとめて1回**。ラウンド1〜12が終わった時点で、保留した論点を集約して `AskUserQuestion` で聞く。ラウンドごとの小出しは禁止（ユーザーの往復が増える）。ラウンド13で新たな論点が出たときだけ、もう一度聞く。
2. 1問につき **論点1行 + 選択肢2〜4**。各選択肢に「選ぶと何がどうなるか」を添える。推奨があれば先頭に置き `(推奨)` と付ける。
3. **待っている間に手は止めない**。論点に依存しない `B`・`M` は先に直しておく。
4. 回答が来たらその通りに直す。**回答と違う判断はしない**。
5. 報告に `ユーザー判断:` 行として残し、`dev_log.md` にも判断理由を1行書く。

やってはいけないこと: 論点を黙って片方に倒して「修正済み」と報告する／論点を `m` に格下げして見送る／選択肢を出さずに「どうしますか？」とだけ聞く。

### ラウンド13（総合）

修正後の差分に対して、1体だけ起動する。渡すのは「1〜12で出た指摘一覧（対応/見送り/ユーザー判断の別つき）」と修正後の差分。見るのは:

- 各指摘が本当に解消されているか（言葉だけでコードが変わっていない、を捕まえる）
- 修正によって新たに壊れた箇所がないか
- 差分がスコープを超えて膨らんでいないか

**ラウンド13で `B` が出たら直して、ラウンド13をやり直す**（最大3回）。3回で収束しなければ「収束せず」として残件をユーザーに出す。

## 最後に必ずやること

```bash
for f in tests/test_*.py; do python3 "$f" >/dev/null 2>&1 || echo "FAIL: $f"; done
```

モデル・特徴量・ランキングロジックに触れた場合は、これに加えて `bear-backtest` スキルで数値を出す（CLAUDE.md §4 改善マージ規律: 平均リターン・勝率・大勝率のいずれも改善しない変更はマージ禁止）。

## 報告フォーマット

```
修整指示: <1行要約>
対象差分: N files, +X/-Y

ラウンド1-12: 指摘 B=a / M=b / m=c / ?=e（却下 d件）
  [B] core/rank_stocks.py:142 drop_prob が None で TypeError → 修正済み
  [M] lib/utils.py:88 「直近60日」が63日 → 修正済み
  [m] web/export_to_web.py:30 ログ文言 → 見送り（差分膨張のため）
  [?] core/screener.py:64 「直近60日」の解釈が営業日/暦日で割れる → ユーザーに確認
ユーザー判断: 「直近60日」は営業日（回答どおり `window=60` の営業日で実装）
ラウンド13: 残 B=0 / 新規破壊なし / スコープ逸脱なし
テスト: tests/ 21件 pass（bear: 平均 +X.X% / 勝率 XX%）
判定: 完了 / 要判断（未回答の論点があれば列挙）
```

完了後、`dev_log.md` に1行追記してからコミットする。

## トークン規律

- レビュアーには**差分と観点だけ**を渡す。ファイル全文を貼らない。
- 各レビュアーの返答は指摘のみ（最大5件）。要約や前置きを書かせない。
- ラウンド1〜12で `B`・`M` が0件のバッチが2回続いたら、残りのラウンドは**まとめて1体**に投げて短縮してよい（13観点を全部見ることは維持する）。
